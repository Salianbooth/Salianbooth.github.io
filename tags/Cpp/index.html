Sequential Access VS Random Access

  • 随机访问（Random Access）：在非易失性存储（例如硬盘）上进行随机访问通常比顺序访问要慢得多。这是因为硬盘的机械性质决定了读取不同位置的数据需要移动磁头，会产生额外的寻道时间和延迟。

  • 顺序访问（Sequential Access）：指的是数据按连续的物理位置依次进行访问，这样的访问模式更高效，因为不需要频繁移动磁头。

DBMS 会尽量优化数据的存储和访问，以最大化顺序访问的使用，原因是这样能提升整体性能：

  1. 减少对随机页面的写入次数：
    • DBMS 通过算法尽量减少对随机页面（散乱分布的页面）的写入，以保证数据被存储在连续的块中。
  2. 同时分配多个页面（Extent）：
    • 当需要分配多个页面时，DBMS 会一次性分配相邻的多个页面，这种方式被称为一个扩展区（Extent）。这样可以尽量保证数据的物理连续性，从而提高顺序访问的可能性。

System Design Goals

在课程中提出了DBMS的设计目标：

  • Allow the DBMS to manage databases that exceed the amount of memory available.

  • 允许数据库管理系统（DBMS）处理超出内存容量的数据库。

  • Reading/writing to disk is expensive, so it must be managed carefully to avoid large stalls and performance degradation.

  • 磁盘读写开销较大，因此需要精细管理。

  • Random access on disk is usually much slower than sequential access, so the DBMS will want to maximize sequential access.

  • 需要最大化的利用顺序存储。

Disk-Oriented DBMS

磁盘导向的DBMS中更新数据的基本流程：
在disk硬盘上的database file中存储了我们的pages，其中通过directory page来找到想要的几号pages；将想要的update 的pages加载到buffer pool缓冲池中，燃后execution engine get page#2，然后更新数据，最后将page#2存储回到database file中。

  1. 磁盘管理 (Disk Management)：
    • 主要职责：负责将数据库存储为磁盘上的一个或多个文件。这些文件可能是以专有格式存储的，操作系统通常不了解其内部结构。
    • 工作方式：磁盘管理器负责在磁盘上组织数据，以页 (pages) 的形式存储。每个页面都有唯一的标识符，数据和元数据都存储在这些页中。
  2. 缓冲池管理 (Buffer Pool Management)：
    • 主要职责：将从磁盘读取的页面暂时存储在内存中（缓冲池）以提高性能。数据库系统不能在每次需要数据时都直接访问磁盘，因为这会导致较大的性能开销。
    • 工作方式：缓冲池管理器从磁盘中获取页面，将其缓存到内存中以便快速访问。它需要决定哪些页面应该留在缓冲池中，哪些页面可以被替换掉。
  • 磁盘管理决定了数据如何在磁盘上存储和组织，而缓冲池管理则负责将这些存储在磁盘上的数据页加载到内存中，并优化页面的读写操作以减少对磁盘的频繁访问。
  • 缓冲池管理依赖于磁盘管理：缓冲池中的页面需要由磁盘管理器提供，当页面不再缓存在内存中时，缓冲池管理器会通过磁盘管理器从磁盘上获取数据。
  • 二者目标一致：共同减少昂贵的磁盘I/O操作。缓冲池管理通过将页面保留在内存中来减少磁盘访问，而磁盘管理通过优化文件存储和读取顺序来减少随机访问的性能开销。

Why not use OS

The DBMS can use memory mapping (mmap) to store the contents of a file into the address space of a program.
DBMS 可以使用内存映射（mmap）将文件的内容存储到程序的地址空间中。

OS is responsible for moving file pages in and out of memory, so the DBMS doesn’t need to worry about it.
操作系统负责将文件页面在内存和磁盘之间进行调度，因此 DBMS 不需要对此进行关心。

我们可以通过下面的流程了解os对文件进行调度：

  1. mmap 映射：当程序使用 mmap 进行文件映射时，操作系统会将文件的某些部分（通常以页为单位）映射到程序的虚拟地址空间中。但此时，并没有实际将文件的数据加载到物理内存中。
  2. 程序访问虚拟内存页面：当程序访问映射到虚拟地址空间中的某个页面（例如 page1），操作系统会检查该页面是否已经在物理内存中。
    • 如果页面已经在物理内存中，程序就可以直接访问该页面的内容。
    • 如果页面不在物理内存中（通常这是第一次访问时的情况），就会触发缺页中断。
  3. 缺页中断和页面加载：缺页中断（Page Fault）发生时，操作系统会负责从磁盘上的文件中读取该页面的数据，并将其加载到物理内存中。加载完成后，虚拟内存中的这个页面就会和物理内存中的实际页面关联起来。此后，程序访问该页面时，数据就直接从物理内存中读取。

    但是当物理内存满了后会怎么样呢？mmap遇到页面错误，这将阻止进程，如果进程锁定了其他元组就麻烦了。

Memory Mapped I/O Problems

Problem #1: Transaction Safety
→ OS can flush dirty pages at any time.

  • 操作系统可以随时刷新脏页。

Problem #2: I/O Stalls
→ DBMS doesn’t know which pages are in memory. The OS will stall a thread on page fault.

  • 数据库管理系统（DBMS）不知道哪些页面在内存中。发生页面错误时，操作系统会导致线程停顿。

Problem #3: Error Handling
→ Difficult to validate pages. Any access can cause a SIGBUS that the DBMS must handle.

  • 难以验证页面的有效性。任何访问都可能导致 SIGBUS 错误，DBMS 必须处理这些错误。

Problem #4: Performance Issues
→ OS data structure contention. TLB shootdowns

  • 操作系统的数据结构争用。TLB（翻译后备缓冲区）失效。

Page

DBMS中通常把文件切分成大小固定的一块数据->page页。每个page页面能存储元组，meta-data元数据，indexes，log等等，大多数的system不会mix page types（每种数据都有专门的page存储）。每个 page 带着一个唯一的 id，DBMS 使用一个 indirection layer 将 page id 与数据实际存储的物理位置关联起来。

A page is a fixed-size block of data.
→ It can contain tuples, meta-data, indexes, log records…
→ Most systems do not mix page types.
→ Some systems require a page to be self-contained.

Each page is given a unique identifier. → The DBMS uses an indirection layer to map page IDs to physical locations.

关于pages，有三个概念需要区分：

  • Hardware Page：通常大小为 4KB

Tuple-oriented Storage（基于元组的存储）

Strawman Idea: Keep track of the number of tuples in a page and then just append a new tuple to the end.
初步想法：记录页面中的元组数量，然后只需将新元组追加到页面末尾。

但是这样会有几个问题：
-> 如果我们删除了中间某一个元组怎么办？ —–> 一旦出现删除操作就要遍历一遍，寻找空位。
->如果我们有一个变长的对象呢？

为了解决上述的问题，slotted pages 就诞生了。

Slot Array

Index-oriented Storage

DBMS stores a table’s tuples as the value of an index data structure.
DBMS将一个表的元组存储为索引数据结构的值。
→ Still use a page layout that looks like a slotted page.
→ 仍然使用类似于带槽页面（slotted page）的页面布局。

Tuples are typically sorted in page based on key.
元组通常根据键在页面中排序。

Tuple Storage

  • 元组本质上是一个字节序列。数据库管理系统负责解释这些字节并将其解析为不同的属性类型和值。
  • DBMS使用系统目录中的模式信息（Schema），根据表的定义来理解元组的布局。这意味着存储的数据类型及其排列方式都由系统提前定义。

Data Layout

  • 元组存储时包含表头信息以及实际的属性值。DBMS需要理解这些字节以确定它们对应的具体字段。
  • 例如，在存储表AndySux中的数据时，表头会保存每个字段的相关信息，而id和value字段分别存储其对应的数据。

Word-aligned Turple

  • 为了让CPU能够有效地访问元组，DBMS会确保元组中的所有属性是字对齐（word-aligned）的，这可以避免非对齐读取所带来的额外工作或意外行为。

  • 例如，一个64位CPU访问一个不对齐的32位数据时，可能会发生非对齐读取，导致性能下降。

    现在有以下的几种方法：
    方法 1：执行额外的读取
    → 执行两次读取来加载数据字的适当部分并将它们重新组装。
    方法 2：随机读取
    → 读取一些意外组合的字节，将其组装成一个64位字。
    方法 3：拒绝
    → 抛出一个异常，并希望应用程序能处理它。

Padding

  • 填充（Padding）：在属性之间添加空白位，确保每个属性按字对齐方式存储。

Reordering

  • 重新排序（Reordering）：通过调整属性在元组中的顺序来减少填充的需求，从而提高存储效率。

Data Representation

  1. 整数类型：

    • INTEGER/BIGINT/SMALLINT/TINYINT：这些整数类型的存储方式与C/C++语言中的相同。

  2. 浮点数与定点数：

    • FLOAT/REAL vs. NUMERIC/DECIMAL：浮点数使用IEEE-754标准进行存储，而定点数则是基于固定小数点表示法。

  3. 可变长度的数据类型：

    • VARCHAR/VARBINARY/TEXT/BLOB：这些数据类型会存储一个长度标识符，接着是实际的数据字节，或者指向数据存储位置的指针。使用这些类型时还需考虑排序和字符集等问题。

  4. 时间与日期类型：

    • TIME/DATE/TIMESTAMP/INTERVAL：这些类型通常存储为自Unix纪元以来的秒数或微秒数。

  5. 浮点数的精度：

    • 浮点数（如FLOAT、REAL）使用可变精度的原生C/C++类型存储，尽管它们可以快速计算，但不能保证完全准确的值。

  6. 定点数的精度：

    • NUMERIC/DECIMAL类型允许使用任意精度，适用于对精度要求严格的场景。这些类型通常存储为变量长度的二进制数据，并附带元数据。

  7. 处理NULL值的几种方式：

    • Bitmap Header：用一个集中位图来标识哪些字段为NULL。
    • 特殊值：为每种数据类型指定一个特殊值代表NULL。
    • Per Attribute Flag：每个属性都有一个标识位表示其是否为NULL，但这种方式会影响字对齐。

  8. 大值存储：

    • 对于超过单个页大小的值，数据库系统会使用溢出页来存储。例如，Postgres的TOAST机制允许存储大于2KB的值，其他系统如MySQL和SQL Server也有类似的溢出页机制。

  9. 外部值存储：

    • 有些系统允许将大值存储在外部文件中，例如Oracle的BFILE和Microsoft的FILESTREAM。这些外部文件无法由数据库系统直接管理，因而缺乏持久性和事务保护。

在C++中，智能指针（Smart Pointers）是一种用于自动管理动态内存分配的工具，它确保对象在不再使用时自动释放内存，避免手动调用 delete 导致的内存泄漏和其他问题。智能指针基于 RAII（资源获取即初始化）的理念管理资源的生命周期。

2.2 POLA

在 C++ 和软件设计的背景下，POLA 是 “Principle of Least Astonishment”（最小惊讶原则）的缩写。这一原则也被称为最小惊讶原则或最小意外原则，它主张设计系统时，应该遵循用户或程序员的直觉，避免让他们感到意外或困惑。

1. POLA 的基本概念

POLA 的核心思想是：代码、接口、或库的行为应该符合用户的期望，从而避免在使用时出现惊讶或意外的结果。这一原则在编写代码时很有用，因为它能提高代码的可读性、可维护性，并减少出错的几率。

2. POLA 在 C++ 编程中的应用

在 C++ 中，POLA 可以在多个层面上应用，涵盖代码设计、库设计、函数行为等，以下是几个常见场景：

2.1 函数和运算符的预期行为

在重载运算符或函数时，必须遵循 POLA，使得用户直观地理解它们的行为。例如：

  • 如果重载 + 运算符，用户通常会期望它是相加操作，而不是减法或其他操作。如果行为与标准运算符不一致，会让用户感到意外。

  • 构造函数应该初始化类的成员，并确保类的对象在构造后处于有效的状态。如果构造函数不进行适当的初始化，用户可能会感到意外。

2.2 接口设计

设计类和函数的接口时，也需要遵循 POLA。例如：

  • 函数的返回值：用户调用一个函数时，通常期待返回值与函数名相关。例如，一个名为 getValue() 的函数，用户会期望它返回某个值，而不是修改对象的内部状态。

  • 合理的默认参数：当函数提供默认参数时，应该保证这些默认参数不会导致意外行为。默认参数应符合常见的使用场景，而不是稀有的边界情况。

2.4 错误处理和异常

在错误处理方面，程序设计应该避免让用户意外地收到异常或错误信息。例如：

  • 隐式转换：如果隐式转换可能导致模糊或不明确的行为，那么这种设计不符合 POLA。用户可能期望使用特定类型而不会产生副作用。
  • 合理的异常抛出：如果函数有可能抛出异常，用户应该能够预测到。否则，程序可能会在用户意外的地方崩溃。

当使用资源（如内存、文件句柄）时，用户期望资源能够自动释放，因此应该遵循 RAII（Resource Acquisition Is Initialization）原则，避免内存泄漏和资源未正确释放的情况。

良好的命名能够帮助遵循 POLA。函数、变量和类的名称应该清晰地表达它们的意图。用户通过名称应该能够推测出它们的功能，避免意外误用。

  • 减少 Bug 和错误：用户意外的行为往往会导致 Bug。如果程序的行为总是符合预期，用户就能更容易理解并正确使用代码，减少出错的机会。

  • 抽象类包含纯虚函数，不能直接实例化，用于定义接口或基础功能。

这些概念共同构成了 C++ 中的面向对象编程，特别是在实现多态性和代码复用方面。

2.1默认边界

在C++标准库（STL）中，容器的默认访问方式并不会启用边界检查，具体来说，使用下标运算符 [] 访问容器元素时不会进行边界检查，而使用 .at() 方法时会启用边界检查。

1. 下标索引 []：

  • 不进行边界检查：如果访问超出容器范围的元素，行为是未定义的（Undefined Behavior, UB），通常会导致程序崩溃或不确定的错误。
  • 适用场景：如果你确信访问的下标是合法的，并且你追求性能，使用 [] 会更高效，因为它不增加额外的开销。

2. .at() 函数：

  • 启用边界检查：如果尝试访问超出范围的元素，会抛出 std::out_of_range 异常。边界检查虽然稍微增加了运行时开销，但能显著提高安全性。
  • 适用场景：适合在你不确定下标是否安全的情况下使用，或者在需要处理异常时。

对比总结：

  • []：没有边界检查，性能较高，适合在高性能需求和确保下标合法时使用。
  • .at()：有边界检查，较为安全，在超出范围时抛出异常，适合安全性更高的场景。

一般来说，都用[]。

  1. 简化代码：std::stack 限制了操作，只允许在栈顶插入和删除元素。这种限制让代码更简洁，容易理解和维护，避免了对 std::vector 的不必要操作。

  2. 明确数据结构的意图：使用 std::stack 可以明确你的意图是要使用后进先出的数据结构，而不是一个通用的动态数组。这样，其他阅读代码的人可以迅速了解数据的处理方式。

  3. 避免误用：std::stack 通过封装 std::vector，限制了对容器的操作。这种限制帮助避免了不适合栈操作的其他操作，比如随机访问和在中间插入或删除元素。

  4. 符合设计原则：C++的设计原则之一是**“尽量封装实现，暴露接口”**。std::stack 通过提供栈操作的专用接口，实现了这一原则，让开发者只关注栈相关的操作，而不需要关心底层的实现细节。

3.Invalidation of Iterators

迭代器失效指的是迭代器指向的容器发生变化后，迭代器不再有效，使用它可能导致未定义行为。不同容器对迭代器失效的情况有所不同：

3.1 常见的迭代器失效情况

  • 插入元素：在某些容器中，插入元素后，所有或部分迭代器会失效。

    • std::vector：如果插入元素导致重新分配内存，则所有迭代器失效；否则只有插入位置之后的迭代器失效。
    • std::deque 和 std::string：类似 std::vector，内存重新分配后，所有迭代器失效。
    • std::list 和 std::set：插入不会使任何迭代器失效。

  • 删除元素：从容器中删除元素后，可能会导致迭代器失效。

    • std::vector：删除操作会使被删除元素之后的迭代器失效。
    • std::list：删除单个元素只会使指向该元素的迭代器失效，其他迭代器保持有效。
    • std::map 和 std::set：同样，只会使指向被删除元素的迭代器失效。

  • 内存重新分配：如 std::vector 扩容或缩容时，重新分配内存会导致所有迭代器失效。

  • 容器销毁：如果容器被销毁，指向它的所有迭代器都会失效。

  1. eofbit（end-of-file bit）

4.Input/Output Stream

4.1 Flush

  1. 缓冲流：字符先存储在一个中间缓冲区中，然后才会被移动到外部目标。

    • 当你在编写程序时，输出的数据（例如字符或字符串）并不会立刻被发送到终端、文件或其他外部设备。相反，这些数据会先存储在一个临时的内存区域中，这个区域称为缓冲区。缓冲区用于暂时存储数据，直到有足够的数据积累后再一起发送，以提高程序的性能。

  2. 为了将字符推送到外部目标，必须“刷新”流。

    • 如果你想立即将缓冲区中的数据发送到外部设备或目标（例如，显示在屏幕上或写入文件中），需要刷新流。刷新操作会将缓冲区中的所有数据立刻发送出去，而不是等待缓冲区填满或者程序结束时自动刷新。

对于cout来说，有一些特殊情况：
cout（标准输出流）通常情况下会使用缓冲区来暂存数据，而不是每次输出操作后都立即刷新到屏幕。这种缓冲机制可以提高输出操作的效率。不过，有几种情况会触发 cout 自动刷新缓冲区：

  1. 遇到换行符（\n）时：

    • 在大多数实现中，当 cout 输出一个换行符（\n）时，它会自动刷新缓冲区，将所有已输出的数据立即发送到屏幕。这是为了确保换行之前的内容及时显示。

    在这个例子中，Hello, world! 后的 \n 会触发 cout 的自动刷新。

  2. 使用 std::endl 时：

    • std::endl 是一个特殊的操作符，它不仅会插入一个换行符，还会强制刷新 cout 的缓冲区。

    在这个例子中，std::endl 不仅会输出换行，还会立即刷新缓冲区。

  3. 程序正常结束时：

    • 当程序正常结束或 cout 被关闭时，标准库会自动刷新 cout 的缓冲区，将所有未输出的数据发送到屏幕。

  4. 当 cin 被使用时：

    • 如前所述，当 cin 开始读取输入时，标准输出缓冲区也会自动刷新，以确保所有输出的内容在输入提示之前已经显示给用户。

Q&A

  1. When does the program prompt the user for input?
    程序何时提示用户输入？

    • The program prompts the user for input whenever an input operation like cin >> is encountered, and it requires data to be read from the standard input. If there is no data in the input buffer or the program needs more data, it will “hang” and wait for the user to provide input.
      每当遇到 cin >> 之类的输入操作时，程序都会提示用户输入，并且它要求从标准输入中读取数据。如果 input buffer 中没有数据或程序需要更多数据，它将 “挂起” 并等待用户提供 input。

  2. Why does the cout operation not immediately print the output onto the console? When is the output printed?
    为什么 cout 操作没有立即将输出打印到控制台上？何时打印输出？

    • cout is buffered, meaning it stores output data in a buffer and doesn’t necessarily print it immediately to the console. The output is printed when:
      cout 是缓冲的，这意味着它将输出数据存储在缓冲区中，并且不必立即将其打印到控制台。在以下情况下打印输出：
      • The buffer is full.
      • A newline (\n) is encountered, which often triggers a flush.
        遇到换行符 （\n），这通常会触发 flush。
      • std::endl is used, which inserts a newline and forces a flush.
        std：：endl 的 intent 插入换行符并强制刷新。
      • The program finishes or exits, which triggers a flush.
      • std::flush is explicitly called to manually flush the buffer.
        显式调用 std：：flush 来手动刷新缓冲区。

  3. Does the position pointer skip whitespace before the token or after the token with each >> operation?
    位置指针在每次 >> 操作时是否会跳过令牌之前或之后的空格？

    • The position pointer skips whitespace before the token with each >> operation. This means that when extracting a value using cin >>, any leading spaces, newlines, or tabs are ignored before reading the actual token.
      位置指针在每次 >> 操作中跳过标记前的空格。这意味着，使用 cin >> 提取值时，在读取实际标记之前，将忽略任何前导空格、换行符或制表符。

  4. Does the position pointer always read up to a whitespace? If not, provide a counterexample.
    位置指针是否总是读取到空格？如果没有，请提供一个反例。

    • The position pointer generally reads up to a whitespace, which is why it stops reading tokens like integers, floats, or strings when it encounters spaces, newlines, or tabs.
      位置指针通常读取到空格，这就是为什么当遇到空格、换行符或制表符时，它会停止读取整数、浮点数或字符串等标记。

    • Counterexample: Consider the input "86.2". If you extract an int from this input:

      int number; std::cin >> number;

      The int extraction reads up to the first non-numeric character, stopping at the decimal point, so number would be 86. The position pointer will then be positioned at the decimal point, not a whitespace.
      反例：考虑输入 “86.2”。如果从此输入中提取 int：int 提取最多读取第一个非数字字符，在小数点后停止，因此数字将为 86。然后，位置指针将位于小数点，而不是空格处。
