算法思想：在包含问题的所有解的解空间树中，按照深度优先搜索的策略，从根节点出发深度搜索解空间树。当搜索到某一节点时，要先判断该节点是否包含问题的解，如果包含就从该节点出发继续深度搜索下去，否则逐层向上回溯。一般在搜索的过程中都会添加相应的剪枝函数，避免无效解的搜索，提高算法效率。

5. 更新或创建新的节点

  • 判断是否是最后一个字符：当到达 key 的最后一个字符时，我们创建一个带有 value 的 TrieNodeWithValue 节点来存储该值。
  • 递归构建子节点映射：否则，我们会沿着 Trie 树继续向下构建子节点。
  • 如果到达最后一个字符，就创建一个 TrieNodeWithValue<T> 节点，并传入 new_value 和当前的 new_children（相当于构造了一个包含新值的新节点）。

  • 遍历结束后，new_children 包含了从根节点到 key 的新路径。

存储过程

存储过程（Stored Procedure） 是一段预编译的 SQL 代码，保存在数据库中，可以重复调用。你可以将存储过程理解为一个可以执行的 SQL 脚本，适用于需要重复使用或复杂的业务逻辑操作。

本身就是用来封装一段SQL语句，进行复用，我的理解就是这个是可以没有return的函数（但是这只是粗浅的理解，实际上存储过程和函数区别和使用场景有着挺大的不同的）

可以包含多种 SQL 语句，适合更复杂的操作，包括插入、更新、删除和事务控制。存储过程可以处理数据修改、事务管理等复杂

存储过程的优点：

  1. 提高性能：存储过程在创建时被编译，执行时效率较高；而且通过减少客户端和服务器之间的通信，可以提升执行效率。

  3. 封装复杂逻辑：复杂的业务逻辑可以被封装在存储过程内，客户端只需调用存储过程，而无需关心其内部实现。
  4. 安全性：通过存储过程可以控制用户对数据库的访问权限，避免直接执行 SQL 操作。
  5. 事务支持：存储过程内部可以控制事务，确保数据的完整性和一致性。

缺点：

  1. 调试困难：相比应用程序中的代码，调试存储过程中的逻辑更加困难。
  2. 可移植性差：不同的数据库管理系统（如 MySQL、PostgreSQL、Oracle）对存储过程的支持存在差异，代码的移植性较差。
  3. 维护复杂：随着存储过程的数量增加，数据库中的逻辑复杂度也会增加，维护变得更加困难。

适用场景：

  1. 批量处理：存储过程适合批量更新或操作多个表的场景。
  2. 业务逻辑封装：将业务逻辑集中在数据库端，通过存储过程控制业务流程，如订单处理、库存管理等。
  3. 事务处理：多步数据库操作中需要确保数据一致性时，存储过程可以通过事务控制完成复杂操作。
  4. 复杂查询：需要执行多个查询、插入、更新或删除操作时，可以将这些操作封装在存储过程内。

事务处理

在复杂的操作中，存储过程通常会使用事务来确保数据的一致性。

当我们在进行存储过程时，假设这个过程中，数据库出现故障，那会怎么办呢？数据库中有可能会出现我们所不知道的空行或者不完整的表单。如何解决这种问题？这时候就需要使用事务处理。

那么事务处理到底是什么呢？事务处理是一种机制，用来管理必须成批执行的SQL操作。

使用事务处理，可以保证一组操作不会中途停止，它们要么完全执行，要么完全不执行。如果发生错误，则进行回退。

事务有四个重要的特性，称为 ACID 特性：

  • 原子性（Atomicity）：事务中的所有操作要么全部完成，要么全部不完成。任何一个操作失败，整个事务就会回滚到事务开始前的状态。
  • 一致性（Consistency）：事务执行前后，数据库的完整性约束没有被破坏。
  • 隔离性（Isolation）：并发执行的事务彼此之间不应相互影响，每个事务的中间状态对其他事务是不可见的。
  • 持久性（Durability）：一旦事务提交，其对数据库的更改是永久性的，即使系统崩溃也不会丢失。

MySQL 提供了一些用于控制事务的语句：

  • START TRANSACTION 或 BEGIN：开启一个新的事务。
  • COMMIT：提交事务，将所有操作的更改保存到数据库中。
  • ROLLBACK：回滚事务，撤销自上次 START TRANSACTION 以来的所有操作。
  • SAVEPOINT savepoint_name：设置一个事务保存点，可以在回滚时回到该保存点。
  • ROLLBACK TO SAVEPOINT savepoint_name：将事务回滚到指定的保存点。

语句解析：

  • SIGNAL：这个关键词用于触发错误或异常。
  • SQLSTATE '45000'：SQLSTATE 是一个标准的 SQL 错误代码，表示某种错误类型。'45000' 是一个通用的自定义错误代码，表示一个用户定义的异常（即不属于标准 SQL 错误）。这是个比较常用的自定义错误状态码。
  • SET MESSAGE_TEXT = 'Insufficient balance'：使用 SET 设置触发的错误消息文本。MESSAGE_TEXT 是 MySQL 中用于存储错误信息的一个属性。'Insufficient balance' 是我们想要返回给用户的自定义错误信息，表示“余额不足”。

事务处理的好处

  • 数据一致性：通过原子性和隔离性保证操作不会因失败而导致数据不一致。
  • 错误处理：可以在事务内捕获错误并选择是否回滚。
  • 并发控制：通过隔离级别管理并发操作对数据的影响。

在 MySQL 中，游标（Cursor）是用于遍历查询结果集的数据库对象。它可以逐行地访问查询的每一行记录，非常适合在存储过程或触发器中处理复杂的逻辑，例如批量操作、逐行处理数据等。

游标的特点

  1. 逐行处理：游标允许在存储过程中逐行访问查询结果集，而不是一次性地返回整个结果。
  2. 状态管理：游标有不同的状态（如打开、关闭、结束）来控制对数据的访问。
  3. 适合复杂逻辑：在需要对查询结果进行逐行处理或复杂计算的情况下，游标非常有用。

使用游标的基本步骤

  1. 声明游标：定义游标并关联一个查询语句。
  2. 打开游标：打开游标以开始读取数据。
  3. 读取数据：使用 FETCH 语句从游标中逐行提取数据。
  4. 关闭游标：完成操作后，关闭游标释放资源。

游标的示例

假设有一个表 employees，结构如下：

employee_id first_name last_name salary
1 John Doe 5000
2 Jane Smith 6000
3 Bob Brown 7000

我们将编写一个存储过程，逐行遍历这个表的数据，并在控制台输出每个员工的姓名和薪水。

游标的工作流程

  1. 声明游标：在存储过程中定义游标 employee_cursor，该游标执行一个 SELECT 查询，获取 employees 表中的所有记录。

  2. 声明处理程序：使用 DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1; 来声明一个异常处理程序，当游标到达结果集的末尾时，会将 done 变量设为 1，从而结束循环。

  3. 打开游标：通过 OPEN employee_cursor; 打开游标，准备逐行读取数据。

  4. 读取数据并处理：使用 FETCH 语句从游标中提取数据到变量中，直到 done 变量被设置为 1 时结束循环。

  5. 关闭游标：完成读取操作后，通过 CLOSE employee_cursor; 关闭游标，释放资源。

详细解析

  • DECLARE employee_cursor CURSOR FOR ...：定义一个游标 employee_cursor，其结果集为 SELECT employee_id, first_name, last_name, salary FROM employees;。

  • DECLARE CONTINUE HANDLER FOR NOT FOUND ...：定义一个处理程序，处理游标读取到结果集末尾的情况，设置 done 变量为 1 以退出循环。

  • OPEN employee_cursor：打开游标，使其可以读取数据。

  • FETCH employee_cursor INTO ...：逐行从游标中读取数据，并将其存入之前声明的变量中。

  • IF done = 1 THEN LEAVE read_loop;：检查 done 是否为 1，如果是，则退出循环（表示结果集已经读取完毕）。

  • CLOSE employee_cursor：关闭游标释放资源。

游标的应用场景

  1. 批量更新/插入：当需要对结果集的每一行进行复杂处理并更新时，例如计算薪水、调整库存等，游标非常有用。
  2. 逐行处理逻辑：一些业务逻辑可能要求对表中的每一行数据进行检查和处理，这些操作很难通过简单的 SQL 语句实现，这时游标就派上用场了。
  3. 复杂报告生成：当需要根据表中的数据生成详细报告时，游标可以逐行访问数据，汇总和计算信息。

注意事项

  1. 性能问题：游标逐行处理数据，在大数据集上效率较低。如果可能，尽量使用批量操作和集合操作来代替游标。
  2. 资源管理：游标需要显式地打开和关闭，否则可能会导致资源泄露。

总结

  • 游标 是在 MySQL 中遍历查询结果集的一种工具，适用于存储过程中需要逐行处理数据的场景。
  • 通过游标，我们可以逐行读取、处理、更新数据，适合复杂的业务逻辑和逐步操作。
  • 但由于游标可能带来性能开销，在可能的情况下，应优先考虑批量操作或其他替代方法。

Sequential Access VS Random Access

  • 随机访问（Random Access）：在非易失性存储（例如硬盘）上进行随机访问通常比顺序访问要慢得多。这是因为硬盘的机械性质决定了读取不同位置的数据需要移动磁头，会产生额外的寻道时间和延迟。

  • 顺序访问（Sequential Access）：指的是数据按连续的物理位置依次进行访问，这样的访问模式更高效，因为不需要频繁移动磁头。

DBMS 会尽量优化数据的存储和访问，以最大化顺序访问的使用，原因是这样能提升整体性能：

  1. 减少对随机页面的写入次数：
    • DBMS 通过算法尽量减少对随机页面（散乱分布的页面）的写入，以保证数据被存储在连续的块中。
  2. 同时分配多个页面（Extent）：
    • 当需要分配多个页面时，DBMS 会一次性分配相邻的多个页面，这种方式被称为一个扩展区（Extent）。这样可以尽量保证数据的物理连续性，从而提高顺序访问的可能性。

System Design Goals

在课程中提出了DBMS的设计目标：

  • Allow the DBMS to manage databases that exceed the amount of memory available.

  • 允许数据库管理系统（DBMS）处理超出内存容量的数据库。

  • Reading/writing to disk is expensive, so it must be managed carefully to avoid large stalls and performance degradation.

  • 磁盘读写开销较大，因此需要精细管理。

  • Random access on disk is usually much slower than sequential access, so the DBMS will want to maximize sequential access.

  • 需要最大化的利用顺序存储。

Disk-Oriented DBMS

磁盘导向的DBMS中更新数据的基本流程：
在disk硬盘上的database file中存储了我们的pages，其中通过directory page来找到想要的几号pages；将想要的update 的pages加载到buffer pool缓冲池中，燃后execution engine get page#2，然后更新数据，最后将page#2存储回到database file中。

  1. 磁盘管理 (Disk Management)：
    • 主要职责：负责将数据库存储为磁盘上的一个或多个文件。这些文件可能是以专有格式存储的，操作系统通常不了解其内部结构。
    • 工作方式：磁盘管理器负责在磁盘上组织数据，以页 (pages) 的形式存储。每个页面都有唯一的标识符，数据和元数据都存储在这些页中。
  2. 缓冲池管理 (Buffer Pool Management)：
    • 主要职责：将从磁盘读取的页面暂时存储在内存中（缓冲池）以提高性能。数据库系统不能在每次需要数据时都直接访问磁盘，因为这会导致较大的性能开销。
    • 工作方式：缓冲池管理器从磁盘中获取页面，将其缓存到内存中以便快速访问。它需要决定哪些页面应该留在缓冲池中，哪些页面可以被替换掉。
  • 磁盘管理决定了数据如何在磁盘上存储和组织，而缓冲池管理则负责将这些存储在磁盘上的数据页加载到内存中，并优化页面的读写操作以减少对磁盘的频繁访问。
  • 缓冲池管理依赖于磁盘管理：缓冲池中的页面需要由磁盘管理器提供，当页面不再缓存在内存中时，缓冲池管理器会通过磁盘管理器从磁盘上获取数据。
  • 二者目标一致：共同减少昂贵的磁盘I/O操作。缓冲池管理通过将页面保留在内存中来减少磁盘访问，而磁盘管理通过优化文件存储和读取顺序来减少随机访问的性能开销。

Why not use OS

The DBMS can use memory mapping (mmap) to store the contents of a file into the address space of a program.
DBMS 可以使用内存映射（mmap）将文件的内容存储到程序的地址空间中。

OS is responsible for moving file pages in and out of memory, so the DBMS doesn’t need to worry about it.
操作系统负责将文件页面在内存和磁盘之间进行调度，因此 DBMS 不需要对此进行关心。

我们可以通过下面的流程了解os对文件进行调度：

  1. mmap 映射：当程序使用 mmap 进行文件映射时，操作系统会将文件的某些部分（通常以页为单位）映射到程序的虚拟地址空间中。但此时，并没有实际将文件的数据加载到物理内存中。
  2. 程序访问虚拟内存页面：当程序访问映射到虚拟地址空间中的某个页面（例如 page1），操作系统会检查该页面是否已经在物理内存中。
    • 如果页面已经在物理内存中，程序就可以直接访问该页面的内容。
    • 如果页面不在物理内存中（通常这是第一次访问时的情况），就会触发缺页中断。
  3. 缺页中断和页面加载：缺页中断（Page Fault）发生时，操作系统会负责从磁盘上的文件中读取该页面的数据，并将其加载到物理内存中。加载完成后，虚拟内存中的这个页面就会和物理内存中的实际页面关联起来。此后，程序访问该页面时，数据就直接从物理内存中读取。

    但是当物理内存满了后会怎么样呢？mmap遇到页面错误，这将阻止进程，如果进程锁定了其他元组就麻烦了。

Memory Mapped I/O Problems

Problem #1: Transaction Safety
→ OS can flush dirty pages at any time.

  • 操作系统可以随时刷新脏页。

Problem #2: I/O Stalls
→ DBMS doesn’t know which pages are in memory. The OS will stall a thread on page fault.

  • 数据库管理系统（DBMS）不知道哪些页面在内存中。发生页面错误时，操作系统会导致线程停顿。

Problem #3: Error Handling
→ Difficult to validate pages. Any access can cause a SIGBUS that the DBMS must handle.

  • 难以验证页面的有效性。任何访问都可能导致 SIGBUS 错误，DBMS 必须处理这些错误。

Problem #4: Performance Issues
→ OS data structure contention. TLB shootdowns

  • 操作系统的数据结构争用。TLB（翻译后备缓冲区）失效。

Index-oriented Storage

DBMS stores a table’s tuples as the value of an index data structure.

Tuple Storage

  • 元组本质上是一个字节序列。数据库管理系统负责解释这些字节并将其解析为不同的属性类型和值。
  • DBMS使用系统目录中的模式信息（Schema），根据表的定义来理解元组的布局。这意味着存储的数据类型及其排列方式都由系统提前定义。

Data Layout

  • 元组存储时包含表头信息以及实际的属性值。DBMS需要理解这些字节以确定它们对应的具体字段。
  • 例如，在存储表AndySux中的数据时，表头会保存每个字段的相关信息，而id和value字段分别存储其对应的数据。

Word-aligned Turple

  • 为了让CPU能够有效地访问元组，DBMS会确保元组中的所有属性是字对齐（word-aligned）的，这可以避免非对齐读取所带来的额外工作或意外行为。

  • 例如，一个64位CPU访问一个不对齐的32位数据时，可能会发生非对齐读取，导致性能下降。

    现在有以下的几种方法：
    方法 1：执行额外的读取
    → 执行两次读取来加载数据字的适当部分并将它们重新组装。
    方法 2：随机读取
    → 读取一些意外组合的字节，将其组装成一个64位字。
    方法 3：拒绝
    → 抛出一个异常，并希望应用程序能处理它。

Padding

  • 填充（Padding）：在属性之间添加空白位，确保每个属性按字对齐方式存储。

Reordering

  • 重新排序（Reordering）：通过调整属性在元组中的顺序来减少填充的需求，从而提高存储效率。

Data Representation

  1. 整数类型：

    • INTEGER/BIGINT/SMALLINT/TINYINT：这些整数类型的存储方式与C/C++语言中的相同。

  2. 浮点数与定点数：

    • FLOAT/REAL vs. NUMERIC/DECIMAL：浮点数使用IEEE-754标准进行存储，而定点数则是基于固定小数点表示法。

  3. 可变长度的数据类型：

    • VARCHAR/VARBINARY/TEXT/BLOB：这些数据类型会存储一个长度标识符，接着是实际的数据字节，或者指向数据存储位置的指针。使用这些类型时还需考虑排序和字符集等问题。

  4. 时间与日期类型：

    • TIME/DATE/TIMESTAMP/INTERVAL：这些类型通常存储为自Unix纪元以来的秒数或微秒数。

  5. 浮点数的精度：

    • 浮点数（如FLOAT、REAL）使用可变精度的原生C/C++类型存储，尽管它们可以快速计算，但不能保证完全准确的值。

  6. 定点数的精度：

    • NUMERIC/DECIMAL类型允许使用任意精度，适用于对精度要求严格的场景。这些类型通常存储为变量长度的二进制数据，并附带元数据。

  7. 处理NULL值的几种方式：

    • Bitmap Header：用一个集中位图来标识哪些字段为NULL。
    • 特殊值：为每种数据类型指定一个特殊值代表NULL。
    • Per Attribute Flag：每个属性都有一个标识位表示其是否为NULL，但这种方式会影响字对齐。

  8. 大值存储：

    • 对于超过单个页大小的值，数据库系统会使用溢出页来存储。例如，Postgres的TOAST机制允许存储大于2KB的值，其他系统如MySQL和SQL Server也有类似的溢出页机制。

  9. 外部值存储：

    • 有些系统允许将大值存储在外部文件中，例如Oracle的BFILE和Microsoft的FILESTREAM。这些外部文件无法由数据库系统直接管理，因而缺乏持久性和事务保护。

现在有以下的三个目标：

  • 固定长度值：压缩必须生成固定长度的值（可变长度数据除外）。
  • 推迟解压缩：尽量在查询执行的后期才进行解压缩操作，也称为“延迟物化”。
  • 无损压缩：数据库压缩必须是无损的，以确保不会丢失数据。

2.2 POLA

在 C++ 和软件设计的背景下，POLA 是 “Principle of Least Astonishment”（最小惊讶原则）的缩写。这一原则也被称为最小惊讶原则或最小意外原则，它主张设计系统时，应该遵循用户或程序员的直觉，避免让他们感到意外或困惑。

1. POLA 的基本概念

POLA 的核心思想是：代码、接口、或库的行为应该符合用户的期望，从而避免在使用时出现惊讶或意外的结果。这一原则在编写代码时很有用，因为它能提高代码的可读性、可维护性，并减少出错的几率。

2. POLA 在 C++ 编程中的应用

在 C++ 中，POLA 可以在多个层面上应用，涵盖代码设计、库设计、函数行为等，以下是几个常见场景：

2.1 函数和运算符的预期行为

在重载运算符或函数时，必须遵循 POLA，使得用户直观地理解它们的行为。例如：

  • 如果重载 + 运算符，用户通常会期望它是相加操作，而不是减法或其他操作。如果行为与标准运算符不一致，会让用户感到意外。

  • 构造函数应该初始化类的成员，并确保类的对象在构造后处于有效的状态。如果构造函数不进行适当的初始化，用户可能会感到意外。

2.2 接口设计

设计类和函数的接口时，也需要遵循 POLA。例如：

  • 函数的返回值：用户调用一个函数时，通常期待返回值与函数名相关。例如，一个名为 getValue() 的函数，用户会期望它返回某个值，而不是修改对象的内部状态。

  • 合理的默认参数：当函数提供默认参数时，应该保证这些默认参数不会导致意外行为。默认参数应符合常见的使用场景，而不是稀有的边界情况。

2.4 错误处理和异常

在错误处理方面，程序设计应该避免让用户意外地收到异常或错误信息。例如：

  • 隐式转换：如果隐式转换可能导致模糊或不明确的行为，那么这种设计不符合 POLA。用户可能期望使用特定类型而不会产生副作用。
  • 合理的异常抛出：如果函数有可能抛出异常，用户应该能够预测到。否则，程序可能会在用户意外的地方崩溃。

当使用资源（如内存、文件句柄）时，用户期望资源能够自动释放，因此应该遵循 RAII（Resource Acquisition Is Initialization）原则，避免内存泄漏和资源未正确释放的情况。

  • 减少 Bug 和错误：用户意外的行为往往会导致 Bug。如果程序的行为总是符合预期，用户就能更容易理解并正确使用代码，减少出错的机会。
  • 提高用户体验：对于开发库或 API 的开发者来说，遵循 POLA 能让使用者更愉快地使用接口，不需要反复查阅文档来确认每个函数的行为。

模板实例化是C++模板编程中的一个核心概念，它是指编译器根据模板的定义和传入的具体类型，生成对应的具体代码的过程。模板实例化会在程序编译过程中发生，并生成针对具体类型的函数或类代码。

模板实例化的基本原理

当你定义一个模板时，实际上并不会生成任何代码。模板就像一个蓝图或占位符，只有在实际使用模板时，编译器才会根据传入的具体类型生成对应的函数或类。这就是模板实例化的过程。

模板实例化可以分为以下几种方式：

  1. 隐式实例化（Implicit Instantiation）
  2. 显式实例化（Explicit Instantiation）
  3. 显式特化（Explicit Specialization）

1. 隐式实例化

隐式实例化是最常见的模板实例化方式，发生在你调用模板时。编译器会根据传入的参数类型，自动推导模板的类型参数，并生成对应的代码。这种方式最常用，且不需要开发者额外干预。

模板实例化的机制

模板实例化是在编译期完成的，编译器在模板的使用点根据传入的类型生成模板代码。模板实例化的具体机制可以分为以下几个步骤：

  1. 类型推导：编译器根据模板函数或类的参数类型推导出模板参数。
  2. 模板生成：根据推导出的模板参数，编译器生成一个具体的模板实例。
  3. 代码生成：编译器为这个模板实例生成具体的代码。

重复实例化问题

模板实例化在每个使用模板的翻译单元（即每个 .cpp 文件）都会单独生成代码，这可能导致重复实例化问题，尤其在大型项目中，代码的重复生成会增加编译时间和最终的可执行文件大小。

为了解决这个问题，可以通过显式实例化或使用 inline 指令让编译器优化实例化行为。

解决重复实例化的方法：

  1. 显式实例化：在某个 .cpp 文件中显式实例化模板，确保每个类型的实例化只生成一次。
  2. inline 关键字：对于模板函数，可以使用 inline 关键字让编译器优化实例化行为，避免重复生成代码。
